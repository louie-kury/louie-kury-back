# 프로젝트 검증

ECC verification-loop를 프로젝트에 맞게 각색했다. [출처·라이선스](../../../docs/ai/UPSTREAM.md).

1. 현재 경로·Git 상태와 이번 변경을 확인한다. staged/unstaged뿐 아니라 untracked 파일도 확인한다. 최초 커밋 전에는 HEAD나 HEAD~1이 존재한다고 가정하지 않는다.
2. [ROUTING](../../../docs/ai/ROUTING.md)과 [확인된 명령](../../../docs/ai/SETUP.md#commands)에서 영향에 맞는 검사를 고른다. 현재 제품 스택·제품 테스트는 없으므로 제품 명령을 추측하거나 하네스 검사를 제품 검증으로 부르지 않는다.
3. 하네스 Python·설정 변경은 프로젝트 루트에서 `python3 -B scripts/ai/harness.py verify`. 문구 수정만 있으면 관련 내용·링크만 확인한다. 이 명령은 JSON/TOML·스킬 기본 구조와 하네스 회귀 검증이며 보안·제품·Codex 이벤트 검증을 대신하지 않는다.
4. 제품 스택 도입 시 실제 build/typecheck/lint/관련 테스트와 기존 CI 명령을 조사해 SETUP에 연결한다. 실패한 관련 검증은 원인을 확인하고 수정한다. 범위 밖 실패는 별도로 보고한다. 자동 업데이트나 전면 수정으로 덮지 않는다.
5. 같은 코드·환경에서 이미 통과한 유효한 검증은 재사용하고, 관련 변경·실패·미해결 우려가 있을 때 다시 실행한다. 고정 시간·매 편집·임의 커버리지 수치로 전체 검증을 강제하지 않는다.
6. 결과는 검사·명령·실제 결과·범위로 정리한다. PASS / FAIL / 미실행을 구분하고 단위·통합·실제 서버/DB·브라우저 결과를 따로 쓴다. 문자열 검색은 보안 검증 완료 근거가 아니다. 관련 diff를 확인하고 남은 위험과 다음 단계를 적는다.
