# 프로젝트 보안 검토

ECC security-review를 각색했다. [출처·라이선스](../../../docs/ai/UPSTREAM.md).

변경 범위와 신뢰 경계부터 확인하고 실제 코드·설정·호출부에서 증거를 찾는다. 현재 제품 스택과 사용자 역할 정책은 미정이다. 특정 DB의 RLS·JWT·쿠키 방식·파일 크기·rate limit 수치를 팀 정책으로 가져오지 않는다.

변경에 해당하는 항목만 선택한다.

- 비밀값: 저장소·로그·인계·브라우저 산출물·CI 출력의 노출과 Git 제외. 실제 값을 보고서에 인용하지 않는다.
- 입력/출력: 서버 검증, 쿼리 바인딩, XSS/CSRF/CORS, 파일 업로드의 경계·실패 조건. 구현과 프레임워크 보호를 확인한다.
- 권한: [PRD의 정보 접근 정책](../../../docs/prd.md)에서 확정된 범위를 확인한 뒤 소유권·배정 관계·역할을 검증한다. 다른 보호자의 기록 열람·수정 실패를 독립 사례로 확인한다. 정책 미정이면 완료 대신 미정으로 쓴다.
- 통화/외부 API: 실제 연동이 생기면 콜백 서명·재전송·멱등성·재시도·타임아웃·실패 복구를 확인한다.
- 여러 인스턴스: 인증·상담 상태·속도 제한·중복 방지에 공유 상태가 필요한지 확인한다. 프로세스 하나에서의 테스트를 분산 환경 검증으로 표현하지 않는다.
- 하네스: 셸에 외부 입력을 평가하지 않는지, 훅 우회 경로·오류 시 동작·인계 권한·출력 상한을 확인한다. 훅과 문서는 완전한 보안 경계가 아니다.

실제 manifest/lock과 해당 런타임의 기존 검사 도구를 사용한다. 필요하면 외부 문서에 버전·공개 API 질문만 보내며 고객 정보·소스·자격증명을 보내지 않는다. 일괄 dependency fix/update나 새 보안 서비스를 임의 도입하지 않는다.

보고에는 위협·경로·파일/라인·재현 또는 검토 근거·영향·개선안, 실행한 검사와 미검증 범위를 적는다. 문자열 검색이나 단위 테스트만으로 전체 보안이 검증됐다고 하지 않는다. 법적·의학적 서비스 정책의 적합성은 이 스킬의 검증 범위가 아니다.
