# Feature Specification: HARNESS-001 역할 정의 검사 보강

**작업 브랜치**: `main` (명세 전용 단계, 별도 브랜치 생성 없음)

**작성일**: 2026-10-29

**상태**: 설계 가능

**입력**: 로컬 프로젝트 doctor가 7개 역할 정의와 project-sdd 진입 스킬의 준비 여부를 올바르게 판단하도록 보강한다. 이 문서는 실제 독립 모델의 명세→설계→작업→구현→검토 흐름을 검증하는 하네스 이슈이며 제품 기능 명세가 아니다.

## User Scenarios & Testing

### User Story 1 - 불완전한 역할 준비 상태 식별 (Priority: P1)

팀원이 프로젝트 doctor를 실행하면 필수 역할의 누락이나 잘못된 필드를 성공으로 안내받지 않아야 한다.

**우선순위 이유**: 잘못된 준비 완료 판정은 이후 역할 실행에 대한 신뢰를 깨뜨린다.

**독립 검증**: 유효한 임시 프로젝트를 준비하고 매번 한 조건만 바꾸어 역할 검사의 성공/실패를 확인한다.

**수용 시나리오**:

1. **Given** 필수 7개 역할과 진입 스킬이 정상인 프로젝트, **When** 역할 준비 검사를 실행하면, **Then** 역할 구성 검사는 성공한다.
2. **Given** 필수 역할 중 하나의 파일이 없는 프로젝트, **When** 검사하면, **Then** 실패한다. 신규 3개 역할 각각의 누락도 포함한다.
3. **Given** 역할의 필수 필드 하나가 누락되거나 빈 문자열 또는 공백만 있는 문자열인 프로젝트, **When** 검사하면, **Then** 해당 필드를 유효하다고 판단하지 않는다.
4. **Given** 필수 필드 하나가 문자열이 아닌 프로젝트, **When** 검사하면, **Then** 값의 진릿값과 무관하게 실패한다.
5. **Given** 역할 파일명과 내부 name이 불일치하거나 서로 다른 역할 파일의 name이 중복된 프로젝트, **When** 검사하면, **Then** 실패한다.

### User Story 2 - 진입 스킬 및 기존 실행 흐름 보존 (Priority: P1)

팀원은 역할 정의가 정상이어도 진입 스킬이 없으면 준비되지 않았음을 알아야 하며, 정상 구성에서는 기존 로컬 Spec Kit 상태 확인을 계속 사용할 수 있어야 한다.

**독립 검증**: 정상 구성에서 진입 스킬 파일만 제거한 사례와 정상 구성을 별도로 검사한다. doctor 실행 경계의 하위 명령 호출 여부 및 종료 결과를 확인한다.

**수용 시나리오**:

1. **Given** 7개 역할은 정상이지만 `.agents/skills/project-sdd/SKILL.md`가 없거나 파일이 아닌 프로젝트, **When** 검사하면, **Then** 실패한다.
2. **Given** 잘못된 역할 또는 누락 진입 스킬이 있는 프로젝트, **When** doctor를 실행하면, **Then** 비정상 종료하며 하위 Spec Kit 상태 확인을 실행해 성공으로 덮지 않는다.
3. **Given** 정상 역할 구성과 정상 로컬 실행 환경, **When** doctor를 실행하면, **Then** 기존 저장소 고정 런타임의 상태 확인으로 이어지고 그 결과를 보존한다.

### 경계 사례

- 필드별로 `""`, 스페이스만 있는 문자열, 탭·줄바꿈만 있는 문자열을 각각 거부한다.
- 필드별로 숫자, 불리언, 배열, 테이블 등 TOML에서 표현 가능한 비문자열을 거부한다. 참인 값도 예외가 아니다.
- description과 developer_instructions는 앞뒤 공백을 제외하고 내용이 있는 문자열이면 유효하다. 내용의 의미·문장 길이를 추가 정책으로 판단하지 않는다.
- name은 공백 제거로 다른 이름을 자동 보정하지 않고 파일명 stem과 정확히 일치해야 한다.
- 읽을 수 없거나 파싱할 수 없는 역할 TOML을 준비 완료로 처리하지 않는다.
- 추가 역할 파일에 필수 역할의 name을 복제한 경우에도 중복을 놓치지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 필수 역할은 `spec_author`, `spec_planner`, `spec_implementer`, `spec_reviewer`, `spec_verifier`, `security_reviewer`, `stack_advisor`의 총 7개이며 `.codex/agents/<name>.toml`로 존재해야 한다.
- **FR-002**: 각 역할 TOML의 필수 필드는 `name`, `description`, `developer_instructions`의 3개다. 각 값은 문자열이며 공백 제거 후 내용이 있어야 한다.
- **FR-003**: 역할의 name은 해당 역할 파일명 stem과 정확히 일치해야 하며, `.codex/agents/` 바로 아래 역할 TOML 파일들 사이에서 유일해야 한다. 추가 역할 자체를 금지하지 않지만 그 파일도 필수 필드와 이름 규칙을 따라야 한다.
- **FR-004**: 필수 역할 누락, 필수 필드 누락·빈 문자열·공백 문자열·비문자열, 이름 불일치·중복, TOML 파싱·읽기 실패 중 하나라도 있으면 역할 준비 검사는 실패해야 한다.
- **FR-005**: `.agents/skills/project-sdd/SKILL.md`는 파일로 존재해야 하며, 누락 또는 파일 아닌 경로는 실패해야 한다. 스킬 본문의 의미 검증은 요구하지 않는다.
- **FR-006**: doctor는 역할 준비 실패 시 실패 결과를 반환하고 하위 상태 확인으로 진행하지 않아야 한다. 정상 구성에서는 기존 하위 상태 확인과 종료 결과 전달을 보존해야 한다.
- **FR-007**: 각 실패 조건을 독립적으로 드러내는 회귀 검증을 남겨야 한다. 정상 7개 역할 구성이 통과하는 양성 검증도 포함한다.

### Key Entities

- **역할 정의**: 파일 경로와 name, 설명, 실행 지시로 구성되는 프로젝트 공유 역할 설정.
- **필수 역할 집합**: 명세·설계·구현·리뷰·검증·보안·스택 자문 책임을 담당하는 7개 canonical name.
- **진입 스킬**: 역할 흐름으로 진입하는 프로젝트 공유 `project-sdd` 스킬 파일.

## Success Criteria

- **SC-001**: 정상 7개 역할과 진입 스킬의 양성 사례는 역할 준비 검사에 통과한다.
- **SC-002**: 7개 필수 역할 각각의 누락, 3개 필수 필드 각각의 누락·빈 문자열·공백 문자열·비문자열, 이름 불일치, 이름 중복, 진입 스킬 누락에 대한 개별 음성 사례는 모두 실패한다.
- **SC-003**: 잘못된 구성의 doctor 실행은 성공으로 보고되지 않으며 정상 구성의 하위 상태 확인 결과 전달이 보존된다.
- **SC-004**: 검증 보고는 로컬 설정·회귀 검사, 실제 모델 역할 실행, 원격 CI 및 실제 제품 환경을 구분한다.

## 현재 재현 근거

2026-10-29 명세 작성 시 `scripts/ai/specify.py`의 `check_agents`는 기존 4개 이름만 순회하고 name의 일치 및 description/developer_instructions의 진릿값을 확인한다. 필수 필드는 3개이며 기존 역할 개수가 4개라는 점을 구분한다.

`python3 -`로 `scripts/ai`의 `specify`를 import한 뒤, `tempfile.TemporaryDirectory`마다 역할 파일 복사본과 진입 스킬을 준비하고 `check_agents(temp_root)`를 직접 호출했다. 원본 설정은 변경하지 않았다.

| 독립 사례 | 수정 전 관측 결과 | 요구 결과 |
| --- | --- | --- |
| 기존 4개 역할만 있는 구성 | ACCEPTED | 신규 3개 필수 역할 누락으로 실패 |
| spec_author의 description = `"   "` | ACCEPTED | 공백 문자열로 실패 |
| spec_author의 description = `7` | ACCEPTED | 비문자열로 실패 |
| spec_author의 developer_instructions = `true` | ACCEPTED | 비문자열로 실패 |

이는 직접 호출한 현재 검사 함수의 재현이다. 이름 중복 등 나머지 조건까지 전부 실제 재현했다는 주장은 하지 않는다. `python3 scripts/ai/specify.py doctor`도 실행했으나 uv가 `<uv cache>/sdists-v9/.git` 접근 권한 오류로 종료 코드 2를 반환해 전체 doctor 정상 동작은 확인하지 못했다.

## Assumptions · 미정 · 범위

- 상위 오케스트레이터가 신규 3개 역할 정의를 작성한다. 역할 본문 내용의 적절성은 이번 구조 검사와 별도 검토 사항이다.
- 현재 헌법은 미작성 템플릿이며 템플릿 예시를 새 팀 정책으로 확정하지 않는다.
- 명세 산출물 경로는 사용자 지정에 따라 `docs/ai/validation/HARNESS-001/spec.md`다. 별도 제품 feature, 브랜치, `.specify/feature.json`, 체크리스트 파일을 생성하지 않는다.
- 설계를 막는 요구사항 미정은 없다. 구체적 오류 문구와 검사 구현 방식은 설계 단계에서 선택한다.
- **비범위**: 제품 기능 생성, 기술 스택 확정, 외부 이슈 생성·메시지 전송, 커밋·푸시·배포, 전역 도구 변경, 실제 제품 서버·DB·분산 환경 검증, 역할 모델 실행 성공을 doctor만으로 보증하는 기능.
- 다음 단계는 이 문서를 근거로 한 독립 설계·작업 분해다. 구현 및 전체 수용 기준 실행은 아직 하지 않았다.
