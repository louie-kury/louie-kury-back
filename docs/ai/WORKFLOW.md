# 메인과 네 명의 담당자

다섯 역할이다. **메인은 현재 세션**이므로 별도 서브 에이전트 파일을 만들지 않는다. `.codex/agents/`에는 아래 네 담당자만 등록한다.

| 담당 | 하는 일 | 수정할 수 있는 것 |
| --- | --- | --- |
| 메인 오케스트레이터 | 사용자 대화, 명령/범위 배정, 결과 확인, 단계 통과·재작업 판단 | 사용자가 허용한 설정·통합 작업. 다른 담당의 범위를 몰래 대신 처리하지 않는다 |
| planner | 처음 설계, 마지막 문서 동기화 | 지정된 설계·API·안내 문서 |
| implementer | 합의한 설계 구현·버그 수정 | 실제 구현 코드와 허용된 구현 설정. 테스트 수정 금지 |
| tester | 기대 결과에 맞춘 테스트 작성·실행 | 테스트 코드·전용 fixture와 허용된 테스트 설정. 실제 구현 수정 금지 |
| reviewer | 코드 리뷰 또는 별도 호출의 블랙박스 QA | 파일 수정 없이 읽기·안전한 실행 결과 보고 |

## 순서

`메인 → planner(design, 필요 시) → 사용자 구현 허가 → implementer → tester → reviewer(code-review) → 새 reviewer(qa) → planner(docs-sync) → 메인 최종 확인 → 요청받은 PR → 팀원 검토·사람 머지`

- **처음 planner:** 설계가 없거나 변경이 필요한 경우 투입한다. 유효한 설계가 있으면 재사용한다. 바이브 와이즈로 사용자의 접근법·선택·이유를 먼저 확인하고 [명세 틀](templates/spec.md)에 기록한다. 선택이 없으면 구현으로 넘어가지 않는다.
- **구현과 검사:** implementer는 테스트를 건드리지 않는다. tester는 구현 버그를 직접 고치지 않고 재현·기대/실제 결과를 메인에게 보낸다. 메인이 구현 버그면 implementer에게, 잘못된 테스트면 근거를 확인한 후 tester에게 돌려보낸다. 변경 후 영향받은 검사만 다시 실행한다.
- **reviewer 두 번 분리:** 코드 리뷰용과 QA용은 서로 다른 새 에이전트 호출이다. 한 reviewer에 두 작업을 묶거나 follow-up으로 모드를 바꾸지 않는다. QA에는 내부 코드 풀이 대신 명세·API 계약·사용자 흐름·확인된 실행 주소를 전달한다. 서버가 없거나 실행하지 못하면 QA는 실행 불가이며 통과가 아니다.
- **마지막 planner:** 최종 구현·테스트·두 검토 결과를 받아 API 라우트·입출력·권한·실패 응답과 관련 문서를 실제와 맞춘다. 버그에 맞춰 요구사항을 낮추지 않는다. 의미가 바뀌면 메인과 사용자의 결정으로 돌아간다.
- **메인 최종 확인:** 변경 파일 소유권, 검사/리뷰/QA 결과와 미실행 범위, 문서의 실제 일치를 확인한다. 문서 동기화 중 코드/계약이 바뀌면 관련 검사부터 다시 진행한다. 실행 불가 단계는 사용자에게 알려 판단받고, 메인이 스스로 성공 처리하지 않는다.

## 설계 결정 기록

합의한 주요 설계 결정은 ADR(Architecture Decision Record)로 남긴다. 결정 하나당 배경, 선택과 이유, 영향을 짧게 적는다.

- 한 서비스에만 적용되는 결정은 해당 서비스 레포의 `docs/adr/`에 기록한다. 예를 들어 상품 서비스의 내부 데이터 모델을 바꾸면 관련 코드와 ADR을 상품 레포의 같은 PR에 포함할 수 있다.
- 여러 서비스가 함께 따르는 결정은 공통 문서 레포의 `docs/adr/`에 기록한다. 서비스 경계, 서비스 간 API·이벤트 계약, 공통 하네스 배치가 이에 해당한다.

## 짧게 위임하기

메인은 작업 목적·설계/사용자 결정·허용 파일·완료 기준·실행 명령/환경과 모드를 전달한다. 전체 대화를 복사하지 않는다. 실제 경로는 manifest와 파일을 보고 정하며 아직 없는 제품 경로를 추측하지 않는다. tester가 테스트를 실행하는 등 배정된 명령은 담당자가 수행할 수 있으나, 단계 판정과 다음 명령의 배정 책임은 메인에 있다.

planner의 질문은 메인이 사람에게 전달하고 답을 되돌려준다. 서브 에이전트가 사용자의 답을 만들어내거나 기다리지 않고 구현하지 않는다. 설계 질문을 위해 별도 에이전트를 추가하지 않는다. 작성 담당자가 같은 파일을 동시에 수정하지 않게 한다.

설계·문서·리뷰만 요청받으면 해당 단계만 수행한다. 이슈 자동 생성, 무조건 전체 단계 실행, 긴 승인 문자열은 사용하지 않는다. 메인은 [대화에서 확인](HUMAN_GATES.md)하고 중요한 선택과 진행 단계는 `$project-handoff`에 저장한다.

## 실제 권한의 한계

이 표는 담당별 작업 규칙이다. 역할 파일은 부모 세션의 도구·권한을 상속하며 파일별 OS 접근 차단을 만들지 않는다. 메인이 diff/실행 결과로 위반을 확인하고 중단한다. [OpenAI 공식 에이전트 설정](https://learn.chatgpt.com/docs/agent-configuration/subagents)을 따른다. 모델·권한 상승·추가 훅은 설정하지 않는다.
